# B0 独立评审 · 光桌 · brand-identity-skill × Gemini 4

评审：Codex / gpt-6-astra，独立于设计执行模型。日期：2026-10-28。阶段：三方向检查点；所有结论为初步信号，不替用户选定方向。

## 结论先行

**初步信号：A 的冷静双栏、B 的印前宋体、C 的工业矩阵确实是三个视觉方向，但不是三个完整的品牌表达系统。** 判断：当前没有一套已经惊艳；A 的“光学比对”机制最有继续推进的潜力，B 最像编辑出版品牌，C 字面最醒目但四宫格最通用。A/B 确实切过「光」，不能说“完全没改字”；仍没有一套重构了「光桌」两字的共同笔画规则。

**B01 的核心缺口重现：现成中文字体主导、同版面同文案、数字搜索漏判。** B02 新暴露出：命名缺少流程、专业工作台并未用真实数字密集场景验证、日志把局部观察扩大成底座能力结论。尤其要纠正“只有 Noto Sans SC 有 tnum”“汉字 16px 必败”“布尔机制无法造字”。本次 `logo-sheet.png` **是最终浅色配色**，没有重演 B01 的旧色联系表问题；反而 `run-log.md` 留有旧色、旧文案和错误源码定位。

## A · 双栏游标 / Split Loupe

### 1. 三套是否真的不同

**初步信号：图形、字重和明暗差异成立，版面与语气差异不足。** 判断：左右括号与中轴竖线、Noto Sans SC 300 的细字、暗青底构成最冷静的一套；与 B 的纯宋体字标、C 的粗窄黑体和方格明显不同。粗框与细字有轻重对照，但尚未形成字与图共享的精密几何语法。

证据：`sets.json:19-21,24-36,61-81,162-164`；tracking 是 **+60**，不是日志所说的“负字距”。三套卡片仍共用同一网格、同一标题“专业创作者的 AI 生图与精修工作台”、同一中英样句、导航与 CTA；最终 `brand.copy` 三份完全相同。不同的机制说明不等于不同的用户沟通语气。

### 2. 换一家 AI / 设计工具是否成立

**初步信号：比泛用星芒更贴“比对”，仍可移植给图像 diff、视频校色或代码编辑工具。** 判断：`[|]` 是清楚的操作隐喻，不是「光桌」独占的身份。相比本次 Krea 的黑底无衬线主页，A 也在“克制专业工具”语汇中，不能把深色当差异本身；相比 Lovart 的白底与荧光黄绿，颜色距离成立。替换成 Midjourney、Leonardo 或即梦的专业比对模块也讲得通，尚不足以证明不可替换。

证据边界：`sets.json:117-120` 写“Krea 纯白底”，但 `site/competitors.json:14-25` 是 `#0a0a0a` 背景、`#0074f0` 强调色，截图也是黑底。A 的竞品论证含实质误读；“Midjourney、Leonardo、即梦普遍暗紫霓虹或星芒”的集合断言未获本次抓取支持。

### 3. 中文字标：画过、好看、结构正确吗

**初步信号：局部改过，字义仍可读；不是专属造字。** 判断：大样「光桌」结构正确，细线干净，但「光」中部的断口更像 stencil 裂缝，“双栏游标”的关联要靠解释；「桌」未改，两字没有共同的新构字规则。细字与厚括号的对照有潜力，也有图强字弱的问题。

证据：Noto Sans SC 300 转曲，首字矩形减法 `x=64,y=36,w=9,h=22`（`sets.json:164`）。只读几何复算确实减少原字标约 **78.51 平方单位 / 1.11% 墨面积**；这个数只证明切口生效，不是设计质量分。没有全字间架重构。

### 4. 16 / 32px

**初步信号：两个尺寸均能保住括号—中线关系；16px 识别的是符号，不是品牌全名。** 判断：32px 两侧开口明确；16px 竖线和框仍分离，但像代码括号/对齐标记，光学仪器含义并不自明。单色不靠青色也可回认，属于可用的简化图形。

实际 `favicon-16.svg` 画布宽 **109.714** 单位，12 单位中线约 **1.75px**，两侧 10 单位间隙约 **1.46px**；不能直接按 100 单位粗算为 1.92/1.60px。最终 logo audit findings 为空，只说明启发式未告警，不是三秒品牌辨识验证。

### 5. 色板、中英混排、大量数字

**初步信号：正文安全，暗色主辅区别偏弱；“浅底游标青 >4.5:1”不准确。** 实测 `#007d8a` 对 `#f3f6f7` 为 **4.49636:1**，四舍五入显示 4.50，但严格低于普通文字 AA 的 4.5；可满足标志图形 3:1，不应直接批准作浅底普通小字。深色主色 `#5a919a` 与强调色 `#1695a3` 已有审计 CIEDE2000 **6.18**，三种色盲模拟差值 **2.88 / 4.37 / 5.72**，不宜仅靠两种青色区分活动/非活动状态。

判断：中英标题轻盈一致，但 300 字重不适合无差别覆盖高密度参数面板。正文数字默认等宽，A 标题数字也等宽；同字族不同字重仍会变宽，详见统一量测。没有真实队列表，不能把一行“4096×4096 / 3.2s”当作高密度数据验证。

## B · 印前校样 / Proof Table

### 1. 三套是否真的不同

**初步信号：主标构成差异最大，语气仍是共用文案。** 判断：不以独立大图标开场，重宋体与红基线很像校样、出版、编辑审稿，明显不同于 A/C 的“左图右字”。但纸本机制没有进入真实批注、编号、精修版本的排版；卡片小应用仍是通用导航＋标题。

证据：`sets.json:181-218,220-255,310`。B 的英文字母也有衬线，和中文标题有一致的阅读气质；不能将这种字体气质直接称为独立语气策略。

### 2. 换一家 AI / 设计工具是否成立

**初步信号：在本次可见 Krea/Lovart 样本里有风格距离，但仍是可搬用的“宋体＋红下划线”编辑品牌。** 判断：换成另一家设计审校工具、出版社、杂志乃至文化咖啡品牌仍成立，名称专属性不够。对即梦“即刻造梦”的想象性表达，B 是流程与审校取向；这是可能的策略距离，不是“全行业唯一用衬线”的证明。对 Midjourney/Leonardo 也只能评价可替换性，无法凭缺失的视觉证据宣称独占。

`sets.json:274-276` 的“AI 工具 97% 以上图标＋文字”未给本类别抽样、分母或测量记录，不作为事实。B 的现代软件定位不能只建立在反科技风上。

### 3. 中文字标：画过、好看、结构正确吗

**初步信号：两字端正、有出版感，改字仍轻；红尺比切口更有存在感。** 判断：大样「光」「桌」无明显错字或缺失部件；粗细对比稳，但「桌」密、「光」疏的结构仍完全由现成宋体决定。首字中竖的短断笔不显眼，基线中间的小凸起更容易被记住；没有把这条规则变成整套中文字的结构。

证据：Noto Serif SC 700、tracking +20；首字切口 `20×9`，红尺 `265×11`、刻度 `11×23`（`sets.json:310`）。只读复算减去约 **149.13 平方单位 / 1.35% 原墨面积**，另加红色图形约 **3047 平方单位**。不能说完全没画，也不能把一刀和装饰基线算作完成造字。

### 4. 16 / 32px

**初步信号：专用 favicon 清楚，但像 π／双柱＋底线，与「光桌」字标的关系偏弱。** 判断：32px 的双竖与红底线稳定；16px 仍能回认，但既不自然读作「光」，也不像日志所称的“四角裁切框＋中心校样框”。实际 SVG 只有上横、两根竖柱和底线（`sets.json:309`），不存在中心红框。

卡片的 64/32/16 单色行展示的是**整词字标按高度缩放**，不是方形 favicon；`identity_card.py:152-156` 有意保留此规则。因此卡片上小字似乎可读，不等于 16×16 标签已验证中文。真正 favicon 使用 `symbol-small.svg`，本评审已单独查看；两种尺寸测试不能混为一谈。

### 5. 色板、中英混排、大量数字

**初步信号：三套中现有文字颜色关系最宽裕，数据角色仍需隔离。** 红色对浅底 **5.90:1**，白字对红色 **6.44:1**；链接对正文 **2.65:1**（深色为 **2.81:1**），仍需下划线等非颜色提示。只有 1 个 warn 不等于整个应用无风险。

判断：宋体标题与黑体正文的中英层级自然，适合说明与编辑文案；Noto Serif SC 700 的数字宽度 **466–596** 字体单位，不能承担计时器/参数列。正文 Noto Sans SC 400 数字全为 **555**；把标题气质延伸到所有表格会破坏对齐。样张没有队列、失败/重试状态或小数位对齐场景。

## C · 批次矩阵 / Batch Matrix

### 1. 三套是否真的不同

**初步信号：字形与图形节奏最硬朗，确有第三方向，但“彻底无圆角”不成立。** 判断：四宫格＋绿红、WDXL Lubrifont SC 的窄字与粗笔给出设备铭牌气氛，与 A 的轻字、B 的宋体区别清楚。实际字标端点、转角明显圆化；图标是直角、文字不是，文案“彻底摒弃圆角”不能照收。

证据：`sets.json:318-320,329-340,459-461`；当前只有方格图标体现模块化，卡片网格和小应用仍与 A/B 共用，未出现自己的批次视觉编排规则。

### 2. 换一家 AI / 设计工具是否成立

**初步信号：三套里最容易成为通用应用启动器／图库／四图生成按钮。** 判断：三实一空能表达“选中一张”，但 2×2 网格很难专属于光桌；换成 Krea、Leonardo、Midjourney 的候选结果、Lovart 的素材资产或即梦多图工具都讲得通。绿色＋朱红和可见 Krea/Lovart 的首页配色不同，却没有改变图形的通用性。

与即梦官网已有的“智能画布、多图融合、局部重绘”功能叙述相比，C 仅把多图生成画成格子，并不自动构成产品差异。此处判断的是可移植语义，不是近似商标或抄袭结论。

### 3. 中文字标：画过、好看、结构正确吗

**初步信号：字体本身有性格，本次没有改字。** 判断：「光」仍可辨；「桌」整体压窄、内部横层密，底部「木」的撇捺被压成近竖向短脚，小一号时更像电子字形而非自然书写。这不是已证实错字，但增加了首读成本。字体圆端与方格直角不统一，不能用“工业”两个字消除差异。

证据：WDXL Lubrifont SC 400、tracking +40，`wordmark_detail_svg: null`（`sets.json:461`）。醒目的中文字形来自字体原设计，不是本轮造字成果。`wordmark-glyphs.json` 中「桌」的 `stems: []` 是扫描漏检，不是该字无竖笔或轮廓损坏。

### 4. 16 / 32px

**初步信号：小尺寸轮廓最稳定之一；稳定的是四格，不是专属性。** 判断：32px 空心右上格清楚，16px 仍能保留内孔和行列缝隙；如果去掉颜色仍可凭空心区别选中格。陌生用户也可能先读作应用菜单、窗口或图库。

最终 favicon 画布宽 **100.571** 单位：12 单位间隙在 16px 下约 **1.91px**，18 单位内孔约 **2.86px**；这些量支持“孔与格未糊合”，不支持“高吞吐、队列完成、进入精修”三种状态都能被读出。

### 5. 色板、中英混排、大量数字

**初步信号：正文可读，红色的使用关系需要限制；窄体标题不能兼任数据字体。** 实测朱红 `#d92b18` 对浅底 **4.41:1**，不满足普通小字 AA；白字置于红底为 **4.87:1**，关系不同。链接对正文仅 **1.38:1**。红色又被指定给“当前精修帧／队列完成／核心触发”，和错误/警报习惯存在冲突风险（判断），应有形状和文字，而不是只靠红绿。

判断：中文工业字与其拉丁窄字协调，但英文长标题、长参数名会显得紧。实际中英样句加载正常；WDXL 数字 advance **264–509**，其中 1 和 7 特别窄，不适合不断变化的队列计数。正文同 A/B，数字默认等宽，尚无真实高密度场景验证。

## 起名：「光桌」与命名流程

**初步信号：名字作为工作台隐喻可继续测试，但本次只提出了一个名字，没有完成命名探索。** 判断：「光」接图像与曝光，「桌」接排队、比较、精修的工作面；两字短、读音明确，比直接“AI＋功能名”更有物理感，也避开“魔法、灵感无限”的常见口吻。缺点是陌生人可能想到灯具/家具，不会自动想到生图；“桌”对手机端是否合适需要实际触点验证。名称好不好不能由一段 light table 故事替用户回答。

### 1. 数字：漏判属实，日志对原因的解释不实

- `scripts/font_audit.py:940-941` 搜索只查目录记录 `features.tnum`；目录中 Noto Sans SC 无该字段、Adobe Blank 有 `tnum=true`。这是 **search 的默认等宽漏判**。
- 审计不是只认标签：`font_audit.py:705-713` 检查 `info['tabular']`；`typelib.py:479-500` 十个默认 advance 相等即返回 `default`。本次 Noto Sans SC 300/400 均实测默认等宽、GSUB/GPOS 均无 `tnum`。
- `pipeline.py:177-191` 按字体族审计，正文角色优先，只有 `audit_role == 'text'` 开 `numbers`；因此 B/C 标题比例数字不阻断是流程定义，不是已验证它们适合表格。
- `pipeline.py:162-191` 对各已配置角色传入全套品牌语言，支持“独立西文 mono 也会接受 zh 覆盖检查”的限制判断；但本次 mono 最终未配置。不能声称脚本强制只能用 Noto Sans SC，更不能把当前目录候选数说成 Google Fonts 全库定论。

### 2. CJK 首次实例化慢：机制存在，路径、字形数与计时要纠正

**初步信号：大字体全量固定字重并去重确有成本；40–60 秒来自执行者记录，不是本评审重新计时。**

真正代码在 `scripts/typelib.py:343-376`，不是日志所写的 `fontlib.py:137-156`（该源码目录没有 `fontlib.py`）。`343-362` 先按源文件 hash＋完整轴位置查缓存，`369-376` 对可变字体调用 `instantiateVariableFont(... overlap=OverlapMode.REMOVE)`；未先做字形子集。`scripts/presentlib.py:582-587` 另有展示字体实例化路径。

本次原始文件实测：Noto Sans SC **31,036 glyphs / 17,772,300 bytes**；Noto Serif SC **31,058 glyphs / 25,125,512 bytes**。不是日志所说两者均 65,535 字形、约 17MB。代码与大文件支持性能风险，但不应把耗时全部归因于去重而忽略实例化其他工作，也不能从一次机器运行推出普遍耗时。缓存命中直接返回是明确的已有缓解。

### 3. 卡片大样硬编码 Aa：属实，但日志定位和影响说过头

准确位置是 `scripts/identity_card.py:284-286`：`<div class="aa" data-role="display" data-fit>Aa</div>`，不是日志的第 142–150 行或 `specimen-aa` 类名。没有按中文语言切换。

### 4. 16px 汉字腐蚀测试“必败”：不成立

`scripts/logo_audit.py:130-146` 做细笔画/窄缝的形态学开闭运算，代码明确标为 **heuristic, uncalibrated**；`455-485` 对实际图形和 favicon 视框检查，最大丢失/填塞区域达到 **0.5px²** 才告警。没有汉字分支、没有“中文直接失败”规则，而且输出是 warn。

日志的「光」约 **1.38px²** 丢失支持“那一版 Noto Serif SC 小图细节有风险”，不能证明所有汉字、所有字重、所有光学校正都必败；“lost strokes”也不等于已经测得“内白坍塌”。没有保存第一轮几何供本次比较，不能还原其全部视觉状态。独立小标是本次可行选择，不是汉字品牌的唯一合法方案。

### 5. “只支持小矩形，无法真正造字”：把默认流程误写成能力边界

`scripts/logolib.py:71` 的形状集合包含 **path**；`1108-1117,1134-1177` 的 `apply_wordmark_detail` 支持按字 union/subtract/intersect、任意允许路径和独立颜色。因此能加笔、删笔、重构轮廓，不限小切口；可编辑能力不等于模型已经做了好字。

初步信号：底座默认从字库转曲、要求一个 ownable detail（`SKILL.md:67-76`），容易引导“切一刀就够”；没有汉字间架、笔性一致性的明确工作步骤。这是流程引导缺口，不是布尔几何无法造字。日志所写 `compose_wordmark/check_small_size` 也不是当前这两处真实实现名。

### 6. 竖笔扫描与 cap-height：方向正确，细节限缩

- `_stems` 在 `scripts/logolib.py:1016-1019`，只保留单扫描线跨度 `<35.0`，**没有日志所称的 `3 < w` 下限**；`1022-1027` 用 `100 - 0.5*x_height` 定扫描高度。C「桌」空、C「光」两个区间，不能说复杂汉字全部失效。

4. **竞品证据不足却使用强结论。** 已有 Krea/Lovart 截图能支持有限色彩/字体对照；不能支持“全行业无衬线、暗紫、97% 图文组合、唯一人文方案”。即梦官方页面也有精细化控制与多图画布，不是只有梦幻宣传词。
